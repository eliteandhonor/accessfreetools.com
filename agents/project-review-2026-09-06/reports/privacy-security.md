### PS-02 [P1] Private OCR/text outputs and Ask proof values lack explicit Clarity masking

- Evidence: `src/components/BaseLayout.astro:117` loads Clarity on public pages. `src/pages/tools/[slug].astro:4105` wraps interactive tools for analytics but does not mask that wrapper. `src/components/AiBrowserTool.tsx:838` renders answers and `:841` renders OCR/text output in ordinary DOM; `:887` renders history. `src/components/AskToolChat.tsx:111` renders the result section and `:131` repeats input values as `<dd>` text. Neither component has a Clarity mask or a masked ancestor in the inspected page wrappers. Infolinks comments at `src/pages/ask.astro:36` and `src/pages/tools/[slug].astro:4101` are ad-scanner controls, not Clarity masks.
- Validation/confidence: high for the missing source controls; conditional, not verified production disclosure. Microsoft's current [masking documentation](https://learn.microsoft.com/en-us/clarity/setup-and-installation/clarity-masking) says Balanced is the default, masks numbers/email addresses, and does not provide blanket page-text protection. Inputs are masked in every mode, but text subsequently rendered outside inputs needs appropriate masking. Explicit element masking is supported. Production project-wide Strict mode/custom selectors were not inspected.
- Scope/trigger: a visitor without analytics opt-out/DNT runs OCR, summary/text tools, or an Ask conversion that repeats private words in its proof output, while the Clarity project has no compensating Strict/custom mask. Alphabetic document content is especially relevant; input masking alone is insufficient after that content becomes page text.
- Impact: private document text or repeated input values can become eligible for third-party session capture despite browser-local inference. This is a privacy boundary gap with high-impact potential, not proof that Microsoft received a particular user's data. React escaping protects against HTML execution but not session recording.
- Minimal task/owner: **Privacy/Security Reviewer + Code Reviewer**: mask the whole user-controlled workspace, including results, errors, history, copied previews, and generated passwords where applicable. Reuse the explicit masking pattern already present in the TTS and JSON-to-CSV pilots. Audit other tool renderers before extending a project-wide privacy claim.
- Acceptance: synthetic unique alphabetic markers in OCR, summary/history, Ask inputs/results, and representative text/password tools remain inside explicit masked ancestors after hydration and rerenders; local browser telemetry interception records no marker in outgoing analytics/Clarity payloads. Verify the configured Clarity settings read-only with owner-authorized evidence before claiming the live gap closed. Do not send real private text to test this.

### PS-03 [P2] MCP execution bypasses the configured REST beta gate and rate limiter

- Evidence: `src/pages/mcp.ts:38` constructs the server/transport and `:47` dispatches the request without `checkApiAccess` or `checkRateLimit`. `src/lib/aftMcpServer.ts:68` registers `run_tool`, which executes the same deterministic registry. In contrast, `src/pages/api/v1/run/[slug].ts:8` and `src/pages/api/v1/ask.ts:8` check access before work. The header-only policy is documented in `docs/ask-api-mcp-alpha.md`.
- Validation/confidence: high, reproduced locally. With a process-only synthetic `AFT_API_BETA_TOKEN` configured, an unauthenticated MCP `tools/call` for `run_tool`/percentage-calculator returned HTTP 200, a result, and no tool error; the unauthenticated REST execution route returned 401. No server listener or production request was used.
- Scope/trigger: deployments with a beta token configured. Without that optional token, REST is intentionally public too, so this is not evidence of private admin-data access. Independently, the MCP route has no application rate gate even in public mode.
- Impact: callers can execute tools outside the configured beta boundary and avoid the REST request quota. MCP exposes deterministic utilities, not arbitrary shell execution, admin reports, or Ollama access; do not inflate the capability gained.
- Minimal task/owner: **API And MCP Tester + Code Reviewer**: define and enforce one explicit execution policy for REST/MCP. If public MCP is intentional, record that exception and its resource limits rather than implying the beta token protects it. Keep public discovery metadata separate if desired.
- Acceptance: with token configured, missing/wrong/query-only credentials cannot execute MCP tools; valid supported header credentials can. Test token-unset behavior, 429/reset behavior, initialize/list/call compatibility, and unchanged no-store responses. Verify the deployed proxy/client-address configuration before claiming per-client production rate guarantees.

### PS-04 [P2] Bounded analytics reads silently omit persisted events from reported totals

- Evidence: `src/lib/siteAnalytics.ts:12` rotates at 25 MiB but `:13` caps each read at 16 MiB. `:324` selects only that tail and `:329` drops a partial first line. `:477` reads those tails and `:491` stops after the event cap. `:573` derives requested-window totals from this already incomplete set; `:619` calls its totals `allTime`. There is no coverage/truncation marker in the summary. `scripts/lib/production-analytics-report.mjs:15` preserves the summary semantics when creating the production aggregate.
- Validation/confidence: high, reproduced against the actual transpiled module with an in-memory filesystem. A 17,825,999-byte current-log fixture containing two valid records separated by blank padding yielded one event, with the first omitted. This proves tail omission, not that the current production log has reached the threshold. The fixture's earlier record was historical; omission of a within-window record follows from the same date-independent tail selection.
- Scope/trigger: any active or archived log exceeds 16 MiB, or the retained event set exceeds 120,000. A full 25 MiB archive permanently loses approximately its first 9 MiB from report reads, even though those bytes remain stored. A requested 30/90/365-day window is not proof that the reader covered that interval.
- Impact: undercounted visits/actions, distorted new/returning classifications, and misleading comparisons presented as complete aggregates. This can misdirect product/promotion decisions. It is not proof that an observed change in production totals was caused by this code.
- Minimal task/owner: **Analytics Reporter + Code Reviewer**: make coverage explicit and prevent incomplete tails from being represented as complete window/all-time totals. Either maintain bounded exact aggregates/streamed window reads or return an honest partial-coverage status with covered dates and limits. Avoid an unbounded file read as the fix.
- Acceptance: fixtures spanning 16/25 MiB, archive boundaries, and >120,000 events produce exact requested-window counts or explicit partial status. Old and recent events in the same file, returning visitors crossing a boundary, and a read during rotation are covered. The production report and dashboard propagate coverage; comparisons remain blocked when continuity is unknown.

### PS-06 [P2] Hosted model routing has no application deadline or disconnect cancellation

- Evidence: `src/lib/askToolRouter.ts:407` calls Ollama without a signal/deadline and `:420` awaits the response body. `:496` waits for that routing call. `src/pages/api/v1/ask.ts:17` awaits the answer without propagating request cancellation. `src/components/AskToolChat.tsx:70` also has no timeout and resets loading only after settlement at `:78`.
- Validation/confidence: high for missing controls, medium for production impact. No stalled live provider request was attempted. Runtime/provider/proxy timeouts may eventually terminate a request; their effective values were not measured here.
- Scope/trigger: an ambiguous <=1,200-character question reaches configured Ollama and the provider or connection stalls. Deterministically parsed questions do not use this network path.
- Impact: the interface can remain disabled until an external timeout, while disconnected callers' upstream requests continue consuming resources. The 60/minute REST gate is not an in-flight concurrency limit.
- Minimal task/owner: **API And MCP Tester + Code Reviewer**: introduce a bounded upstream deadline and propagate cancellation through the routing layer; return a clear unavailable/timeout response without inventing a successful route. Consider a small in-flight cap separately if workload evidence supports it.
- Acceptance: mocked never-settling and slow-body responses are aborted within the specified deadline; disconnect cancels upstream work; UI recovers with a retry path; deterministic parser routes never fetch; raw user text/API keys do not enter error logs or reports. No real model requests needed for regression tests.

## Verified Controls And Important Non-Findings

- **Body limits:** do not file a generic unbounded-body vulnerability based on `request.json()` alone. `astro.config.mjs:44` configures standalone Node with `bodySizeLimit: 131072`. Installed `@astrojs/node/dist/serve-app.js:53` passes the limit through, and `astro/dist/core/app/node.js:294` counts actual streamed bytes. Analytics has an additional 8,192-byte reader/cancellation path at `src/pages/api/analytics/events.ts:23`. Direct route unit calls bypass the adapter and cannot prove production body limits. Full built-server/ingress behavior remains coordinator coverage.
- **Admin access:** both data APIs fail closed for missing/mismatched tokens; header-only auth tests passed. Query tokens are rejected. Admin HTML is a public login shell, not authorization itself. Its private data APIs return `no-store`. No unauthenticated admin read or command-execution path was established. Report refresh uses an allowlisted kind and argument-array `spawnSync`, not a shell-concatenated command.
- **REST authorization:** optional beta token accepts `x-aft-api-token` or bearer headers, not URL parameters. Metadata endpoints are intentionally cacheable; execution endpoints are no-store. Private environment schema fields are marked secret. No actual credential files or values were read for this report.
- **Response headers:** middleware sets HSTS away from localhost, `nosniff`, strict-origin referrer policy, and restrictive camera/microphone/geolocation/payment permissions. Absence of a CSP or frame-ancestors policy is a hardening consideration, not proof of XSS or a reproduced clickjacking attack.
- **Ad consent:** evaluating the actual Infolinks loader with DOM/network stubs produced zero loads for unset consent, denied consent, owner suppression, DNT, GPC, and localhost, and one load for granted production consent. Withdrawal reload logic is present. Public tool/Ask/contact/navigation/footer Infolinks boundaries are present. These source checks do not prove what a remote advertising script injects or captures in production.
- **AdSense:** default disabled; mode selection requires an enabled flag, CMP-ready flag, valid client/slot, and an allowlisted calculator. It suppresses Infolinks on an active AdSense route. A verification meta tag is not ad activation. Publisher approval, certified CMP installation, two-link InText maximum, and disabled other formats are external evidence gates, not established by these flags/tests.
- **Clarity choices:** an isolated loader check confirmed analytics opt-out and DNT suppress loading; denying ads does not suppress Clarity, and GPC alone does not suppress Clarity. The UI has separate advertising/analytics choices. This is a verified distinction, not by itself a legal violation or evidence of personalized advertising. Applicable consent requirements need a separate owner/legal decision before policy compliance is claimed.
- **Model boundaries:** Ask uses fixed HTTPS `https://ollama.com/api/chat`, a server-side key, a 1,200-character message limit, known registry tool names, and deterministic final results. Browser OCR uses local worker/core/language paths. General browser text models permit remote model fallback at `AiBrowserTool.tsx:276`, so do not describe every browser model asset as necessarily self-hosted. This is not evidence that inference text is uploaded. TTS worker model/voice URLs use pinned revisions; parser/preferences/model suites passed. No arbitrary user-selected model host or shell tool was identified in these paths.
- **Production report privacy:** the production collector uses a header token and removes `recentEvents`, `ipHash`, `sessionHash`, and `visitorHash` before writing its aggregate. The report helper tests passed. Dashboard `recentEvents` remain behind admin authorization. Hashes are pseudonymous linkage, not a guarantee of irreversible anonymity under all salt configurations.
